# 通用 MCU 固件流水线：$ARGUMENTS

先按 `embedded-workflow` skill 的**任务模式表**判定本次请求的模式（纯分析/只评审/代码修复/实际烧录），再执行该模式启用的阶段；纯分析与只评审模式不进入编码阶段（若 $ARGUMENTS 未被替换为实际内容，以用户当前消息中的目标描述为准）：

1. **阶段 1 环境分析** — 扫描项目文件 + 结构化提问，产出 Environment Profile。产出前不进入下一阶段。
2. **阶段 2 手册精读** — 严格按任务模式表启用：仅当结论依赖硬件实现时精读对应手册（寄存器/引脚复用、电气限制、时钟、存储器映射、启动/复位、外设时序或 DMA 能力）；纯 C 逻辑或文档问题跳过。需要精读但手册缺失时执行降级策略并告知用户。
3. **阶段 3 编码（仅代码修复/实际烧录模式执行）** — 按 Environment Profile 与手册摘录生成生产级代码（初始化顺序模板、volatile 语义、ISR 纪律、避免无名且散落的配置值）。
4. **阶段 4 硬件评审** — 代码评审或生成后检查先加载 `review-embedded-c`，再按目标架构加载专项清单（review-arm-cortex-m / review-riscv / review-mcs51）；症状排障先查架构清单，涉及 C 语言根因时再加载通用清单。按 `embedded-workflow` 统一严重度和证据规则报告发现；窄范围任务只核查相关路径，全面评审或跨类目改动才逐类完整检查。修复输出**最小可应用 diff**——仅代码修复/实际烧录模式，只评审模式只输出问题、证据与验证建议。
5. **阶段 5 构建门禁** — 按 `embedded-workflow` 的任务模式执行：实际烧录/bring-up 才执行三道门（文件完备→工具链→板子在线），构建/烧录一律**使用工程已有构建系统**（west/pio/UV4/idf.py 等）；仅项目原本没有构建系统或用户明确要求时才生成 Makefile；纯代码任务到门 2 为止——缺工具链只**阻止构建验证**（给出安装命令，工具就绪后补做），不阻止交付代码补丁。

最后按模式呈现：纯分析/只评审——问题清单、证据等级与验证建议；代码修复/实际烧录——环境摘要、评审修复摘要、修复补丁（默认最小 diff，用户要求完整文件时才输出完整代码）、剩余的人工核对建议。只有阶段 2 实际执行时才报告相关手册发现和页码；跳过时简述原因，不补造无关手册引用。各模式末尾附验证状态声明（硬件实测/手册推导/未验证逐项标注）。
