# 通用 MCU 固件开发工作流

三条铁律（凌驾于一切效率考量之上）：

1. **环境先行** — 文件能探测到的信息绝不问用户；探测不到的结构化提问；任何信息不靠猜。
2. **手册为源** — 寄存器值、引脚复用、电气参数以用户提供的 PDF 手册为准；每条摘录必须带文档名+页码，可追溯。
3. **门禁构建** — 缺文件不代造、缺工具给安装指令、板子不在线不烧录；每道门未过就 STOP。

## 任务模式与五阶段流水线

按任务类型启用阶段，避免把每个请求都跑成完整 bring-up：

| 任务模式 | 执行阶段 | 免除项 |
|---|---|---|
| 纯分析（读日志/看代码/查档案） | 阶段 1 摘要 + 阶段 4 症状归因 | 不要求 PDF、工具链、板子在线 |
| 只评审（不改代码） | 阶段 1 摘要 + 阶段 2（涉及寄存器/复用核对时）+ 阶段 4 | 不要求 PDF、工具链、板子在线 |
| 代码修复 | 阶段 1 摘要 + 阶段 2（涉及寄存器/复用决定时）+ 阶段 3/4 | 可离线构建，不要求板子在线 |
| 实际烧录 / bring-up | 全部五阶段 + 三道门 | 无 |

同一任务内阶段按序执行，每阶段产出是下一阶段的显式输入；症状归因可在任何模式下提前发生。

### 阶段 1：环境分析（只读 + 提问，不写任何代码）

先扫描项目文件自动探测，再补问缺口：

| 探测目标 | 文件特征 |
|---|---|
| CubeMX / MounRiver 工程 | `*.ioc`、`*.mxproject` |
| 构建系统 | `Makefile`、`CMakeLists.txt`、`platformio.ini` |
| 商业 IDE | `*.uvprojx`(Keil)、`*.ewp`(IAR)、`.cproject`(CubeIDE) |
| MCU 型号 | 启动文件名（`startup_stm32*` / `startup_ch32v*` / `STARTUP.A51`）、链接脚本、设备头文件 |
| 开发方式 | 库 API 调用（`HAL_*` / `LL_*` / WCH `*_Periph`）/ 裸机寄存器直访 / 两者混合 |
| RTOS | `FreeRTOSConfig.h`、`cmsis_os2.h`、`tx_api.h` |
| 可用手册 | `docs/` 目录（见阶段 2 约定） |

探测前先查板级档案：Glob `docs/board-*.md`——存在则通读（按 `board-profile` skill），以其事实表与规则表为开局基准。档案记录仅在**型号/板卡版本与当前目标匹配且测试日期可信**时优先采信（以档案中标注"硬件实测"的记录为准并向用户确认）；型号不匹配或久未更新的档案只作参考，不得覆盖当前工程探测结果。

探测不到的关键信息（目标型号、工具链、外设需求、晶振频率）用结构化提问补齐。

输出 **Environment Profile**：

```markdown
## MCU 环境档案
**目标型号**: [完整型号，如 STM32F407VGT6 / CH32V203C8T6 / STC8H1K08]
**内核/架构**: [Cortex-M4 / RV32IMAC / 8051(1T)]
**主频上限 / 实际主频**: [xxx MHz]
**Flash / RAM**: [容量与布局]
**开发方式**: [厂商库 / 裸机 / 混合]
**工具链**: [编译器+版本, 构建系统]
**RTOS**: [名称+版本 / 无]
**外设清单**: [外设 → 中断/DMA/轮询 → 用途]
**时钟配置**: [晶振、锁相环、各级总线频率]
**可用文档**: [逐类列出文件名或"缺失"]
**项目结构**: [源码/头文件/链接脚本/启动文件路径]
```

### 阶段 2：手册精读（只读）

手册目录约定（对任何厂商通用，放用户项目根下）：

```text
docs/
├── reference-manual/     # 参考手册：寄存器位域、外设章节、配置时序（最常用）
├── datasheet/            # 数据手册：引脚定义、复用表、电气参数、封装
├── user-manual/          # 用户手册：板级布局、晶振频率、跳线、外设接线
├── programming-manual/   # 编程手册：内核指令、调试接口（Cortex-M / RISC-V）
├── application-notes/    # 应用笔记：实践指南、参考代码
├── technical-notes/      # 技术笔记
└── security-docs/        # 安全公告与加固指南
```

PDF 精读策略：
1. 先读目录（前 1~5 页）定位章节页码
2. 按 15~20 页为单位精读目标章节
3. 跨文档交叉引用（如：数据手册查复用表 + 参考手册查寄存器配置）

纪律：
- 每条摘录标注文档名与页码；**区分 PDF 文件页码与手册印刷页码**，章节/表号一并列出（扫描件无页码时以章节+表号定位）
- 表格按当前决策所需提取相关行列，并注明覆盖范围与未检查部分——禁止为"完整"而大段复制无关内容
- 找不到的信息明确说 "not found"，并指出需要哪类文档、去哪下载（见工具链矩阵表下方）
- 文档版本/型号差异要显式标注

输出 **Documentation Extraction**（含 Source[文档/章节/页码]、寄存器表[偏移/位域/R-W/复位值]、配置步骤序列、交叉引用）。

### 阶段 3：编码（生产级纪律，架构无关）

- 硬件寄存器访问与 ISR 共享变量加 `volatile`（解决可见性问题；**不保证原子性或并发安全**——按访问宽度、编译器与并发场景另行选择临界区/原子操作保护）
- 初始化顺序模板：**时钟使能 → 引脚配置 → 外设寄存器 → 中断控制器 → DMA → 外设使能（最后一步）**——时钟未开就访问寄存器的后果依型号而异（总线错误、读零、写入无效、外设保持复位），按参考手册核对；无论哪种后果，时钟先行都是必须遵守的顺序
- ISR 最小化：清标志、短处理、耗时工作移交主循环/任务；硬件轮询必带超时退出
- 禁止 magic number，一律用厂商头文件宏定义
- 生成完整可编译文件（含全部 include 与原型），不是片段
- 错误处理用返回码，禁止静默失败
- 手册在手时寄存器值以手册为准，注释引用手册章节页码
- 提交前心测编译：include 完整、无未声明变量、类型匹配

### 阶段 4：硬件评审（加载对应架构清单）

按阶段 1 探测到的架构加载专项清单：

- **ARM Cortex-M**（STM32/GD32/NRF/RP2040 等）→ `review-arm-cortex-m`
- **RISC-V**（CH32V/GD32V/ESP32-C 系等）→ `review-riscv`
- **8051**（STC8/STC15/N76 等经典与增强 51）→ `review-mcs51`

路由规则：代码评审/生成后检查 → 按架构清单逐类核查；排障任务（症状已知）→ 直接查对应清单的"症状→原因→修法"表归因，命中后再精读相关类别。

模糊症状协议（用户说不清型号时，如"我的串口打印异常"）——按序执行，绝不跳步：
1. 查板级档案：Glob `docs/board-*.md`，命中即按档案的架构、规则表、症状表直接归因
2. 静默扫工作区推断架构/型号——能探到就不问用户
3. 两者都失败 → **小步分诊**：用户已提供日志/波形时先用现有证据分析，不套固定提问；否则只给 **2~4 条高概率假设**（每条附一个低成本验证动作，明确标注是待验证候选），同时问一个**区分度最高**的问题（如串口类："乱码是否稳定？最近是否改过时钟/晶振？"）；按回答再扩展候选或加载架构清单，绝不连环追问、绝不空猜
4. 拿到型号 → 加载对应架构清单精读归因；症状跨架构或表内未命中 → 回阶段 1 重新分析

评审规范：
- 分级报告：Critical（必挂）/ High（大概率 bug）/ Medium（坏习惯）
- 每条含 `文件:行号` + 问题 + 后果 + 修法
- 每条结论标注**证据等级**：手册/源码直接证实 / 多证据互证 / 经验候选待验证；"经验候选"不作为确定问题报告，并附验证动作
- 修复输出**默认最小可应用 diff**；仅单文件示例或用户明确要求完整替换时才输出完整文件

### 阶段 5：构建门禁（检查 + 放行，不代造）

三道门，逐道过，未过即 STOP 并输出可执行的下一步指令：

**门 1 — 项目文件完备性**：启动文件、链接脚本、系统初始化、设备头文件、main。**先识别构建系统再判定**：Keil/IAR/ESP-IDF/PlatformIO 等工程的基础文件与设备头由设备数据库、软件包或 SDK 管理——不要求复制到项目目录，检查工程引用能否解析即可；GCC+Make/CMake 裸工程按文件在位检查。
裸工程缺任一项：列出缺失清单 + 说明该文件作用 + 指引用厂商工具生成（CubeMX/MounRiver/STC-ISP 工程、厂商 SDK），**绝不自己代造这些文件**；此门未过仅**禁止构建与烧录**——分析、评审与代码补丁仍可继续完成。

**门 2 — 工具链与烧录链**（见下方矩阵）：**编译/构建工具与烧录工具分开判定**——缺编译/构建工具：给出 per-OS 安装命令并**暂停构建验证**（代码补丁仍可交付）；仅缺烧录工具：不影响离线构建与补丁交付，只**阻止烧录验证**。工具就绪后补做对应验证。工具链按检测到的构建系统取用：Keil/IAR 工程用其自带工具链（UV4/IarBuild 等），不套 GCC 矩阵判定。

**门 3 — 目标板在线**：按矩阵检测 USB VID 或串口；未检测到：给出排障步骤（线缆/驱动/Boot 模式/udev 规则），然后停止——门 3 仅**阻止烧录执行**，不影响 Makefile 生成与离线构建。

门 1 与门 2 的编译/构建工具通过 → **优先验证/使用工程已有的构建系统**（Keil/IAR/ESP-IDF/PlatformIO/CMake/Zephyr——重新生成 Makefile 会丢失原工程的宏定义、链接选项与板级配置）；仅当项目原本没有构建系统或用户明确要求时才生成构建 Makefile（板子未连接不阻止生成）：
- 源文件列表、包含路径、链接脚本、启动文件全部来自**实际探测结果**，禁止通配符占位
- 目标：`make`（编译）、`make flash`（编译+烧录，执行前走烧录执行边界）、`make clean`、`make disasm`
- 显式标注需要用户核对的两行：烧录器配置与目标芯片配置

烧录执行边界：**生成烧录命令**与**实际执行烧录**是两步——执行前必须与用户确认目标芯片、连接的烧录设备、是否会擦除现有固件；未获确认不执行擦除或烧录，全片擦除/恢复出厂类操作单独标注风险。

结果分级：**构建成功 ≠ 烧录成功 ≠ 功能实测通过**；对外表述与档案记录只以功能实测为准。

档案钩子：该板**功能实测通过**即按 `board-profile` skill 建初版档案；排障修复后立即追加症状行。

## 表达与报告纪律（全阶段适用）

- 祈使句；完整引脚/寄存器名，禁止"相应 GPIO"式含糊表述。
- 事实用表格、机制用散文、代码只在字节级精确处出现。
- 每条结论必带后果，无后果的删；通用知识已覆盖的不复述。
- 各阶段产出末尾附**验证状态**：硬件实测 / 手册推导（文档名+页码）/ 未验证推断，逐项标注。
- 不写 TODO、不道歉；没验证就写"未验证"并继续。

## 工具链与烧录矩阵

| 架构 | 编译器 | 烧录/调试 | 板载检测 |
|---|---|---|---|
| ARM Cortex-M | `arm-none-eabi-gcc` | OpenOCD / pyOCD / J-Link | USB VID `0x0483`(ST) / `0x1366`(Segger) / `0x2e3a`(CMSIS-DAP) |
| RISC-V (WCH CH32V) | `riscv-none-elf-gcc`(xPack) 或 MounRiver 自带 GCC | OpenOCD-WCH / minichlink / WCH-LinkUtility | USB VID `0x1a86`(WCH-Link/CH34x) |
| RISC-V (ESP32-C3/C6) | ESP-IDF (`riscv32-esp-elf-gcc`) | `esptool` / `idf.py flash` | USB VID `0x303a`(Espressif) |
| 8051 (STC 等) | SDCC 或 Keil C51 | `stcgal` / 官方 STC-ISP（串口冷启动 ISP） | USB 转串口 VID `0x1a86`(CH340) |

板载检测列的 VID 只是**候选识别线索**（如 `0x1a86` 同时覆盖 WCH-Link 与 CH34x 串口）：确认目标在线还需核对 PID/设备名与工具连接结果（如 OpenOCD 连接输出、`esptool chip_id`、stcgal 握手）；用户提供的设备管理器截图或命令输出同样有效。

手册下载渠道：ST.com（RM/DS/UM/AN 全套）、WCH（wch.cn + MounRiver 文档）、Espressif（espressif.com/docs）、STC（stcmcudata.com，中文）。

## 手册缺失时的降级策略

用户暂无 PDF 时：明确告知需要哪类文档；基于通用知识编码时，所有寄存器值与复用配置逐项标注 **"未经该型号手册核对，烧录前需核对"**，并建议尽快补 `docs/`。此模式下仅生成框架代码与通用逻辑分析，**不输出可直接烧录的确定寄存器配置**。

## 未覆盖架构

清单仅覆盖 ARM Cortex-M、部分 RISC-V（WCH/ESP32-C）与 8051。AVR/MSP430/PIC/STM8 等平台按通用五阶段流程执行并明确标注"无专项清单"；评审只用架构无关检查项（volatile、ISR 纪律、初始化顺序、构建门禁），其余以该型号手册为准。
