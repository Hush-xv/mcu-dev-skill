# 板级档案（Board Profile）

核心理念：**档案不是文档。** 文档描述板子；档案改变下次任务开局的行为——不再猜引脚极性、不再踩上次的坑、不再误用兄弟板的教程。每一行必须通过检验：**它防止了哪个具体的错误动作？** 无答案的行删掉。

## 何时查、何时建、何时更新

| 时机 | 动作 |
|---|---|
| 任何固件任务开局（embedded-workflow 阶段 1） | 先 Glob `docs/board-*.md`；有则通读，以其事实表为开局基准 |
| 首次 bring-up 成功（阶段 5 三道门全过） | 建初版档案——哪怕只有事实表和烧录两块，也要建 |
| 排障修复后 | **立即**追加一条症状行（趁记忆新鲜，症状按用户原话记录） |
| 发现新的非显然规则 | 追加规则；写错的规则订正并标注 `[订正: 日期]`，不删除 |

## 文件约定

- 位置：用户项目 `docs/board-<板名或MCU型号>.md`，板名优先——同一 MCU 换板后档案不通用。
- 一套档案 = 一块板。同 PCB 不同 MCU（如 F401/F411、兄弟兼容板）各建一份。
- **档案不替代手册**：寄存器位域仍以 `docs/reference-manual/` 手册为准（embedded-workflow 阶段 2 职责）。档案只沉淀手册不会告诉你的板级事实与踩坑。

## 档案模板（七块，按序）

```markdown
# <板名>（<MCU 完整型号>）

## 1. 事实表
| | |
|---|---|
| MCU | 型号、内核、Flash/RAM、封装、主频上限 |
| 晶振 | HSE/LSE 频率 + 是否出厂焊装 |
| 工作时钟树 | 一组实测可跑的 PLL 配置与各级频率 |
| 关键引脚 | LED/按键/外设——**每脚带极性**（lit=LOW、pressed=LOW、是否需上拉） |
| USB/存储/调试 | 接口形式与枚举设备 |
| 烧录 | 方式、进入手段、枚举出的 VID:PID |

## 2. 规则表（防贵的错误）
1. **<祈使句规则>** —— <后果>。
   （10~15 条封顶；只收通用知识查不到的非显然规则；多余条目下移到坑表。
    好规则的检验标准：后果与症状对不上——"读起来像时钟问题，其实不是"）

## 3. 症状 → 原因 → 修法
| 症状（用户原话） | 真正的原因 | 修法 |
|---|---|---|

## 4. 烧录与恢复梯
- 完整操作序列（按键级）→ 枚举出什么（VID:PID）→ 不枚举时逐级恢复步骤
- 板子**不会自己做**的部分单独标注（如"每次都要手动进 DFU，固件无法自动复位进入"）

## 5. 兄弟板陷阱
- 同 PCB/兼容型号差异（Flash/RAM 容量、传感器通道号、晶振…）
- 网上教程多为哪块板写的、直接抄会错什么

## 6. 配方（已知能编译）
- 从已验证项目抄出的配置文件/时钟树/外设 init——字节级精确才收，注明出处文件
- 不确定能否编译的不收，宁缺勿错

## 7. 验证状态
- 每条"硬件实测"记录附带：**板卡版本、MCU 完整料号、测试日期、测量方法**
- 硬件实测：<逐项列出>；手册推导：<逐项列出，文档名+页码>；未验证：<逐项列出，原因>
- 过期或板卡版本不符的记录降级为"参考"，不作为当前工程依据
```

## 写作纪律

- 祈使句："Enable PWR clock before enabling backup-domain access"，不写"建议"。
- 完整引脚/寄存器名，禁止"相应 GPIO"式含糊表述。
- 事实用表格、机制用散文、代码只在字节级精确处出现。
- 每条规则必带后果；无后果的规则删除。
- 模型通用知识已覆盖的内容不写——档案的价值密度来自排他性。
- 不写 TODO、不道歉；没验证就写"未验证"并继续。

## 与流水线的衔接

- **阶段 1（环境分析）**：查档优先于扫描。档案与文件扫描结果冲突时，以档案中标注"硬件实测"的记录为准，并向用户确认差异。
- **阶段 4（评审）**：目标板有档案时，规则表并入评审前提，症状表用于归因。
- **阶段 5（门禁）**：烧录恢复梯与门 3 的排障输出衔接；三道门全过即触发建档/更新。
