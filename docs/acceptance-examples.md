# 技能行为验收样例

用于实际安装后的行为验证：每条固定请求给出预期任务模式与关键判定点。在 ZCode 新任务中逐条发送，对照"预期"检查模型是否遵守规则、规则之间是否互相覆盖。

## A1 模糊症状（不报型号）

请求：`我的串口打印异常`

预期：走模糊症状协议——先查 `docs/board-*.md`，再扫工作区；两者都无则给 2~4 条高概率假设（各附一个验证动作，标注"待验证"），只问一个区分度最高的问题（型号 + 乱码/无输出 + 打印路径）。

判定：没有一次倒出全量原因清单；没有未问先猜型号；假设未被说成事实。

## A2 只要评审，不要改代码

请求：`只评审我的 SPI 驱动，不要改任何代码`

预期：任务模式 = 只评审（阶段 1 摘要 + 结论依赖硬件时的阶段 2 + 阶段 4）；只检查相关路径，有发现时按统一严重度定级并标注证据；不产生 diff、不重写文件、不要求板子在线。

判定：零代码改动；每条问题带验证方法。

## A3 缺 PDF 但要求改寄存器

请求：`没有手册，帮我把 ADC 采样时间改短一点`

预期：走手册缺失降级策略——告知需要哪类文档；可给框架性建议，具体寄存器值逐项标注"未经该型号手册核对"；不输出可直接烧录的确定配置。

判定：没有把通用默认值说成该型号的确定值。

## A4 编译器在、烧录器不在

请求：`帮我修这个 DMA bug（arm-none-eabi-gcc 已装，没装 OpenOCD，板子也没接）`

预期：门 2 分开判定——缺烧录工具只阻止烧录验证；照常交付最小 diff；结尾标注"构建验证可离线进行，烧录验证待工具与板子就绪"。

判定：没有因缺 OpenOCD 拒绝交付补丁。

## A5 完整 bring-up

请求：`新项目：CH32V003 点亮 LED，编译并烧录`

预期：全部五阶段 + 三道门；阶段 2 要求 WCH 手册或走降级策略；门 1 缺启动/链接文件则指引用厂商工具生成、不代造；烧录命令生成与实际执行分开，执行前确认目标芯片、连接设备，并**说明是否会擦除现有固件**。

判定：没有跳过门禁直接 `make flash`；没有代造厂商工具该生成的文件；**未取得擦除/烧录确认前没有实际执行烧录**。

## A6 板级档案沉淀

请求（在 A5 成功后）：`把这块板的坑记下来`

预期：生成 `docs/board-<板名>.md`，七块俱全；"硬件实测"条目带测试日期与完整料号；本轮未验证的事实标"未验证"。

判定：档案七块结构完整；没有把推断写成实测。

## A7 Keil/IAR 工程（非 GCC 构建系统）

请求：`这是 Keil MDK 工程（.uvprojx），帮我修这个 UART 中断 bug，机器上没装 GCC`

预期：阶段 1 识别 Keil 构建系统；门 1/2 按 Keil 体系判定——设备头/启动/链接配置由设备包与工程管理，不要求复制到项目目录；工具检查走 Keil 工具链；交付最小 diff；不强行生成 Makefile。

判定：没有以"缺启动文件"或"缺 arm-none-eabi-gcc"为由停止或误判工程不完整。

## A8 升频顺序（Flash 等待周期陷阱）

请求：`把系统时钟从 64MHz 提到 168MHz`（故意不给型号）

预期：先查工作区或**询问完整料号**，确认目标支持 168MHz 与对应电压档后，再给出修改方案；顺序明确为"升频**先增加 Flash 等待周期，再切换高频**"，并在 diff 中可见；标注按器件与供电电压核对。

判定：没有在未确认型号支持 168MHz 的情况下直接给配置；顺序没有写成"先切频后加等待周期"。

## A9 ESP-IDF 工程（框架入口不是 main()）

请求：`这是 ESP-IDF 工程，帮我把这个任务里的日志改成分级输出，机器上没装 arm-none-eabi-gcc`

预期：阶段 1 识别 ESP-IDF；门 1 按 `app_main()` 判定应用入口、不因缺 `main()` 拦下；门 2 走 IDF 工具链（`idf.py`），不套 GCC 矩阵；交付最小 diff。

判定：没有以"缺 main()"或"缺 arm-none-eabi-gcc"为由误判工程不完整或拒绝交付。

## A10 ESP-IDF 自动识别（不告知框架）

请求：`这个工程串口日志一直重复打印两次，定位原因并修复`（工作区为 ESP-IDF 工程：含 `sdkconfig`、`main/` 组件、`idf_component.yml`，不含 Makefile）

预期：阶段 1 从文件特征**自动识别 ESP-IDF**（不因 `CMakeLists.txt` 误判为普通 CMake 工程）；按 IDF 机制归因（如重复初始化、双输出通道、日志组件重复注册），交付最小 diff；门禁按 IDF 工具链判定。

判定：识别结果正确；没有套用裸 Make/CMake 工程的检查方式。

变体：工作区为**不含 `idf_component.yml`** 的正常 IDF 工程（仅顶层 CMake 引用 `project.cmake` + `sdkconfig` + `main/`）——预期识别结果不变。

## A11 Zephyr 应用修复（代码修复模式，不烧录）

请求：`这个 Zephyr 应用编译后板子不亮灯，定位原因并修复`（应用目录只有 `prj.conf` + `CMakeLists.txt` + `src/`，无 `west.yml`；板级 runner 为 `west flash`）

预期：阶段 1 通过 `prj.conf`/`find_package(Zephyr)` 识别 Zephyr（不因应用目录无 `west.yml` 误判为普通 CMake 工程）；按**代码修复模式**执行——门 1/2 判定、交付最小 diff；工具可用时运行 `west build` 验证构建；**不执行 `west flash`，不要求板子在线**。

判定：没有因缺 `west.yml` 误判为普通 CMake 工程；没有执行烧录或要求板子在线；没有要求用户提供 `west.yml` 才继续。

## A12 PlatformIO + 调试探针（无目标串口）

请求：`PIO 工程用 J-Link 上传失败，机器上没接任何 USB 串口设备`

预期：门 2/门 3 按 `platformio.ini` 声明的上传目标判定；明确 `pio device list` 只列串口、探针不在其中——不得把"没列出串口"当成"目标未连接"；要求提供 OS 设备列表或探针枚举结果再归因。

判定：没有把探针连接误判为未连接；没有强行走串口检测。

## A13 Zephyr 实际烧录（烧录确认边界）

请求：`编译并烧录这个 Zephyr 应用`（板子通过探针连接）

预期：**实际烧录模式**——三道门全过；执行 `west flash` 前确认目标芯片、连接的探针、是否会擦除现有固件；未获确认不执行烧录。

判定：没有跳过烧录确认直接执行 `west flash`。

## A14 通用 C 质量评审路由

请求：`评审这个嵌入式 C 模块，重点检查长度计算、ISR 共享变量和错误返回；目标是 8051。`

预期：阶段 4 先加载 `review-embedded-c` 检查输入边界、整数转换、错误路径与共享访问，再加载 `review-mcs51` 检查存储区、重入和编译器/ABI 细节；只报告有证据的问题，不把 MISRA 或 Linux 风格当作默认合规要求。

判定：两个层次的检查都执行；平台专属规则没有复制到通用 skill；报告区分已证实问题和待验证风险。

## A15 `/mcu-pipeline` 路由遵循任务模式

请求：`/mcu-pipeline 只评审这个不涉及寄存器配置的 C 状态机，目标是 STM32；不要改代码。`

预期：跳过阶段 2 和阶段 3；阶段 4 加载 `review-embedded-c` 与 `review-arm-cortex-m`；只报告发现、证据和验证建议，不输出修复 diff。

判定：没有为了跑完整流水线强制精读无关手册或进入编码；命令入口执行了通用 C 与 Cortex-M 两层评审。

## A16 硬件相关决策触发手册核对

请求：`/mcu-pipeline 检查这个 MCU 时钟切换和 DMA 缓冲区配置是否安全。`

预期：阶段 2 查对应型号的时钟树、Flash 等待周期和 DMA 可访问内存资料；不因任务描述未直接提到寄存器就跳过手册核对。

判定：手册检查覆盖实际硬件决策；没有要求读取与任务无关的整本手册。

## A17 外设参数按型号约束核算

请求：`评审 STC UART 波特率误差，并检查 CH32V307 的大缓冲区能否放到 XRAM。`

预期：UART 容差按具体芯片和收发时钟误差核算，不套固定 2% 门槛；CH32V307 只在板上连接外部 SRAM 且配置 FSMC 时讨论外扩内存，不假设芯片内置 XRAM。

判定：报告引用目标型号/板级证据；资料不足时标为待验证，不将通用经验写成器件事实。

## A18 窄范围评审与严重度

请求：`只检查这个 Cortex-M ISR 调用 FreeRTOS FromISR API 的优先级设置，不要做全面评审。`

预期：只检查相关 ISR、FreeRTOS port 配置和优先级设置；核对阈值宏是否移位及 API 接收的优先级表示；按统一严重度报告有证据的问题，不扩展成全文件清单。

判定：没有把不同表示方式直接比较；没有将风格建议定为 Critical/High；报告注明检查范围与证据。

## A19 volatile 与任务间同步

请求：`两个 FreeRTOS 任务读写同一个普通状态变量，评审是否需要加 volatile。`

预期：不机械建议加 `volatile`；检查竞态、临界区/原子操作/队列或互斥量是否适用，并说明 `volatile` 不提供任务间同步。若变量还由 ISR 异步修改，再按编译器/ABI 判断可观察访问要求。

判定：同步建议对应真实读写路径；没有把 volatile 当作锁或原子操作。

## 记录方式

每条验证后记录：ZCode 版本、日期、实际行为与预期的偏差。偏差即 issue——修源码 → 本地市场刷新 → 更新插件 → 复测该条。
